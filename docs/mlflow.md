# MLflow Tracking + Model Registry

This project uses a **local, SQLite-backed MLflow store** to track experiments and run a model
registry that drives production model selection. There is no remote tracking server: MLflow is a
training-time tool, and the hosted Vercel site never runs Python (see the bottom of this doc).

## Why

The experiment lab (`scripts/run_model_experiments.py`) compares `local` / `pooled` / `hybrid`
valuation architectures, but it wrote its leaderboard with `CREATE OR REPLACE` — so each run
destroyed the last and the production bundles served a *hardcoded* model regardless of what the lab
found. MLflow fixes both:

1. **History of record** — every lab run and every production training run is a permanent MLflow
   run, so model evolution is auditable over time.
2. **Data-driven serving** — production bundles are registered, and a documented promotion policy
   transitions the best one to `Production`. Serving loads the registry's Production model instead
   of a hardcoded path, with a safe fallback when MLflow is unavailable.

## Store layout

| Path | Committed? | What |
|---|---|---|
| `mlflow/tracking.db` | **Yes** | SQLite tracking store + registry (small: params/metrics/tags only). Required by the registry, which needs a database-backed store. |
| `mlflow/artifacts/` | No (gitignored) | Heavy run artifacts. Regenerated by re-running training. |

Model bundles (~10–70 MB pickles, already gitignored under `artifacts/model-service/models/`) are
logged **by reference** — the run/version records the bundle's path + SHA256 + size as tags, never a
copy. The registry records *which* local bundle is Production; serving loads that local pickle. Set
`MLFLOW_LOG_BUNDLE_ARTIFACT=1` to additionally copy a bundle into the artifact store for a one-off
lineage screenshot.

> The committed `tracking.db` is binary. Commit it deliberately when you mean to publish new history,
> not on every local run. The `-wal`/`-shm` sidecar files are gitignored.

## Experiments and naming

- `property-valuation-lab` — one parent run per lab invocation (`lab/<git_sha7>/<utc>`), with a nested
  child per `architecture × market`. The per-market holdout winner is tagged `is_market_winner=true`.
- `property-valuation-production` — one run per `train_bundle` (`<market>/<model_version>/<utc>`), which
  also registers a version of `vancouver-base-price` / `halifax-base-price`.

## Promotion policy (`scripts/promote_models.py`)

- **Primary metric:** `spatial_cv_mae` (lower wins) — GroupKFold-by-FSA spatial generalization, the
  failure mode that matters for valuation. This is the same metric the lab uses, so the registry
  promotes the architecture that wins on spatial CV.
- **Guardrail:** a candidate may not regress `holdout_mape` vs the incumbent Production version by
  more than `REGRESSION_TOLERANCE` (0.02).
- Per registered model (per market). `--dry-run` prints the decision log without transitioning.

The current registered architectures for Vancouver are `local-per-type` (one model per property type)
and `pooled-features` (one model across all types, with `propertyType` as a feature — the within-market
analog of the lab's cross-market pooling). At production feature-richness these are within ~0.3% on
spatial CV, and the policy selects the winner — a data-driven decision, not a hardcoded one. Halifax is
`local-per-type` only (cross-market pooling would mix listing-price and time-adjusted-sale-price targets).

## Commands

```bash
# Train + log + register production bundles (sets MLFLOW_LOG_TRAINING=1 internally)
.venv/bin/python scripts/train_production_bundles.py

# Promote the spatial-CV winner to Production (and refresh the snapshot)
.venv/bin/python scripts/promote_models.py --dry-run    # show the decision
.venv/bin/python scripts/promote_models.py              # apply

# Refresh the committed registry snapshot (data/exports/model_registry.json)
.venv/bin/python scripts/export_registry_snapshot.py

# Launch the UI
pnpm mlflow:ui      # http://127.0.0.1:5000

# Serve with registry-driven selection (otherwise the committed local bundle is used)
MODEL_REGISTRY_ENABLED=1 pnpm dev:model
```

`scripts/build_all.py` runs the lab → train → promote → snapshot steps in order; each MLflow step
self-skips (exit 0) when MLflow or raw training data is absent.

## Env flags

| Flag | Default | Effect |
|---|---|---|
| `MLFLOW_LOG_TRAINING` | unset | When `1`, `train_bundle()` logs + registers. Set only by `train_production_bundles.py`, so serving-path fallback retrains never pollute the registry. |
| `MODEL_REGISTRY_ENABLED` | unset | When `1` (and MLflow installed), serving resolves the registry's Production model; otherwise the committed local bundle is used. |
| `MLFLOW_LOG_BUNDLE_ARTIFACT` | unset | When `1`, also copy the bundle pickle into the artifact store. |
| `MLFLOW_TRACKING_URI` | local sqlite | Standard MLflow override; tests point this at a tmp store. |

## What to screenshot (for the portfolio)

   `spatial_cv_mae`, winner tag visible.
2. Run comparison across two dated lab invocations — history the old DuckDB `CREATE OR REPLACE` could not keep.
3. `property-valuation-production` runs with `spatial_cv_mae` + `bundle_sha256` lineage.
4. **Models** tab: `vancouver-base-price` (v1 local + v2 pooled) and `halifax-base-price`, with a Production stage badge.
5. `scripts/promote_models.py --dry-run` decision log.
6. `data/exports/model_registry.json` open beside the UI.

## MLflow 2 vs 3

This repo pins `mlflow>=2.14,<3`. MLflow 3 deprecates the staged transitions
(`transition_model_version_stage`, None/Staging/Production) used here in favor of **aliases**. The
pin keeps the staged-promotion UI and policy valid; migrating to aliases (e.g. a `production` alias)
is the forward path when upgrading.

## Hosted deployment note

The Vercel site runs `PUBLIC_MODE` with no Python — MLflow and registry-driven `load_bundle()` are
local/CI only. What ships to the cloud is the committed `data/exports/model_registry.json` snapshot
(and the optional Model-page panel that renders it). `MODEL_REGISTRY_ENABLED` stays unset there.
